01The whole thing in one picture

Every request walks the same corridor. Each gate can turn it away, and each gate is a separate concern with its own file.

Why a wrapper at all? Calling a provider directly from your app means every caller shares one key, nobody can be metered or throttled independently, a provider outage becomes your outage, and swapping providers means editing every call site.

The wrapper is the seam where all of that becomes solvable in one place.

02Life of a request

The synchronous path — POST /v1/complete. Note the order: identity is established before anything is charged, because there is no bucket to charge until you know whose it is.

The endpoint itself is three lines. It parses, delegates to the service, and returns — everything above happens in dependencies and services, which is what makes each piece testable on its own.

03The error taxonomy

Errors are classified by one question: who can act on this? That single question decides the status code, whether we retry, and whether the circuit breaker counts it.

The subtle one. A provider returning 401 becomes a 502 to our caller, not a 401. The credentials at fault are ours. Passing the 401 through would send the caller chasing a problem they cannot possibly fix.

The other subtle one. upstream_circuit_open sits with the provider failures but is not retryable — the breaker exists precisely to stop us from trying.

Every failure comes back in the same envelope, so a client only ever writes one parser:

FieldMeaning
error.codeStable. Branch on this.
error.messageFor humans. May change between releases.
error.detailsOptional structured context (the model name, the upstream status).
error.request_idThe one string that finds every log line for this call.

04Retrying, and knowing when to stop

The retry policy reads AppError.retryable and nothing else. Extending the taxonomy extends the policy for free.

Why the randomness matters. Without jitter, every client that failed at the same instant retries at the same instant. A provider that was just coming back up gets flattened again by the synchronised wave — the "thundering herd".

Full jitter means a uniform pick from [0, cap], not the cap itself. Clients spread out instead of marching in step.

05The circuit breaker

Retrying helps with a blip. During a real outage it actively hurts: every caller queues behind a provider that cannot answer, and their downtime becomes yours.

The breaker's state lives in the process. Run several uvicorn workers and each holds its own view, which is a real limitation and a deliberate one: the fix is a shared store, and that is a different project's problem.

06Authentication

Keys are minted by an operator, shown exactly once, and never stored in a form that could be replayed if the database leaked.

Why a dependency and not middleware? Middleware sees every request, so an auth middleware would also intercept /health, /docs and unmatched paths — leaving you maintaining a path allowlist, the classic source of an accidentally exposed endpoint.

A Depends() is opt-in per route, shows up in the generated docs as an Authorize button, returns a value the endpoint can use, and can be swapped out in tests. Middleware is for work that genuinely applies to everything — request IDs, timing.

07Rate limiting

One token bucket per caller. Tokens accrue continuously and cap at the burst size, so idling buys you a burst but never an unbounded backlog.

Why not a counter per minute? A fixed window of "60 per minute" lets a caller fire all 60 at 11:59:59 and 60 more at 12:00:00 — 120 requests in two seconds, at a limit you believed was 60 a minute.

A bucket has no window boundary to straddle. There is nothing to wait for and exploit.

08Async jobs and webhooks

A completion can take tens of seconds. Holding an HTTP connection open for that is fragile — a dropped connection loses the result, and every in-flight request occupies a worker. So the request is recorded, a 202 comes back immediately, and the answer is pushed to a callback URL later.

How the receiver knows it is really us

Why raw bytes? Re-serialising JSON can reorder keys and change whitespace, which changes the digest. Verify first, parse second.

Why constant-time comparison? A plain == returns early on the first differing byte. Timing that tells an attacker how much of a forged signature was correct, one byte at a time.

Why a separate HTTP client? The upstream client carries the provider's Authorization header. Sending that to a URL the caller chose would hand them our key.

09The data model

Three tables. Everything hangs off the API key, because the key is the identity.

Transactions, and the one deliberate exception

An outage is precisely when you most want to know who was calling. So usage recording is given the session factory rather than the request's session, and is best-effort: a caller who got their completion is never handed a 500 because an analytics write failed.

10How the code is arranged

Two rules keep this honest. Endpoints stay about three lines — anything more belongs in a service. Data structures live in models/, behaviour lives in services/ — whether or not the type crosses a boundary.

The dependency layer is the test seam. Because every service is obtained through Depends(), a test overrides one provider with app.dependency_overrides and the rest of the app is untouched. No monkeypatching, no import-order tricks.

11Tracing and health

Every request gets an id — taken from an inbound X-Request-ID when it looks safe, generated otherwise — returned in the response header, included in error bodies, and bound into every log line that request produces.

Two different health questions

ProbeQuestionChecksIf it fails
GET /health Is this process alive? Nothing at all, deliberately The process is restarted
GET /health/ready Should it be sent traffic right now? Database SELECT 1 and a short upstream probe Pulled from the load balancer, kept alive to recover

Why liveness checks nothing. A liveness probe that fails when the database is down gets the process killed and restarted. That does not fix a database, and it turns a partial outage into a total one.

12Roadmap and known limits

Built in eleven phases, each one adding a capability the previous phase made necessary.

#PhaseStatusWhat it adds
1ContractdoneRequest/response models, generated OpenAPI docs
2Upstream clientdoneLifespan-managed pooled httpx client, service layer, split timeouts
3Error taxonomydoneAppError hierarchy, one envelope, stable codes
4ResiliencedoneRetry with backoff and jitter, budget, circuit breaker
5Client authdoneHashed API keys, caller identity via Depends()
6Rate limitingdoneToken bucket per caller, 429 with Retry-After
7PersistencedonePostgres via SQLAlchemy async and Alembic
8Webhooksdone202, background work, HMAC-signed callback with retries
9ObservabilitydoneRequest IDs into background work, structured logs, readiness
10Testsdone107 across two suites, upstream mocked with respx
11ShipdoneMulti-stage Dockerfile, compose stack, deployment notes

Deliberate limits, each with a clear upgrade

  • Background jobs are in-process. BackgroundTasks runs them on the serving worker's event loop, so a restart loses anything in flight. The job row already holds everything a real queue worker would need, so moving to arq or Celery is mostly relocating JobService.run.
  • Rate limit buckets are per process, so N workers enforce N times the intended limit. The fix is a shared store like Redis — which is why the limiter's check is already async despite doing no I/O.
  • Circuit breaker state is per process, for the same reason and with the same fix.
  • One webhook signing secret for everyone. Per-caller secrets would mean one leak compromises one client rather than all of them.

Natural next steps, none of them required: SSE token streaming (one-directional, so not WebSockets), per-caller webhook secrets, a Redis-backed rate limiter, and a real queue for jobs.
